**Edition 4.0 — Modern Engine-First Architecture Correction · 20 November 2026**

**PLATZ Technologies · Platform for Logic, Art, Tools & Zero Limits · One Place. Zero Limits.**

**Document role.** This is the one product-intent authority for the unified PLATZ application. It describes the complete long-term destination, the properties that cannot be sacrificed, the experience a person must eventually have, and how developers demonstrate real progress. It is not a claim that the software already exists, an immutable choice of programming language or a promise that all advanced capabilities ship immediately. The associated developer directive governs active execution; the repository's measured architecture decisions govern the selected implementation until independently justified changes replace them.

**Permanent product and development principle**

> **Improve the existing PLATZ application in the way that delivers the greatest verified long-term value. Research the best currently available approaches, preserve existing functionality, and prioritize integrated product quality over the number of features or demonstration projects created.**

**Non-negotiable foundation rule.** This is a new, professional game-engine-centered creation platform—not a desktop UI shell with a pretend renderer and not an isometric illustration app. The first significant build must contain authentic GPU-rendered **three-dimensional scene geometry**, a real camera (including perspective), depth/occlusion and transforms, editor controls bound to the same saved scene, interactive runtime behavior and a durable project. An orthographic/isometric camera remains a legitimate *optional view of real 3D*; 2D projection of decorative shapes is not proof of a 3D engine. Existing exploratory code must be evaluated before being promoted, not expanded simply because it runs.

**Modern-technology selection rule.** For this greenfield product, default to the most recent **stable generally available, technically appropriate and maintainable** releases for qualified components, taking measured performance, direct engine control, support and future extensibility into account. No choice may be based chiefly on what is already installed, cheapest to scaffold, fastest to finish a demo, or easiest for the current agent. If a managed .NET component is selected as of 20 November 2026, compare current **.NET 11** to alternatives and favor it over .NET 10 unless a documented technical incompatibility or proven requirement justifies an exception; seek owner authorization before a deliberate older-version greenfield baseline. Neither .NET 11 nor any native language is mandated for the core engine if another architecture wins the complete evaluation.

**One product; no throwaway demonstration app.** Build **one PLATZ application** and **one permanent internal editable validation project** within it. The validation project exists to prove real engine and editor behavior and grows with the product; it is not a second shipped app, separately branded game, disposable prototype, or substitute for actual creation tools. Focused automated testing fixtures may exist independently.

**Breadth with completion.** The purpose is to create many sophisticated capabilities over time; the discipline is to finish each activated capability across the user-facing and technical surfaces it actually affects. Neither endless groundwork nor a rapid accumulation of unfinished buttons satisfies the product vision.

**Evidence vocabulary.** `VISION` means long-term intent; `BACKLOG` means not started; `IN DEVELOPMENT` means work exists but is not ready; `INTEGRATED CANDIDATE` means a working implementation awaits relevant qualification; `VERIFIED` means stated checks passed on a named source revision and environment; `INDEPENDENTLY ACCEPTED` means a separate qualified reviewer approved the applicable evidence; `DEPRECATED WITH MIGRATION` means a successor preserves user value. Do not report a planned capability as delivered. The first frozen baseline is created only after explicit owner acceptance; the current approved master can evolve under recorded change control.

# PART I — THE PRODUCT PLATZ MUST BECOME

## 1. One place for virtually any digital creation

PLATZ is a locally capable, unified, increasingly extensible desktop creation environment and interactive engine. It exists to eliminate the disjointed handoffs among game engines, 3D artists' tools, painting suites, sprite editors, audio/video workstations, coding IDEs, productivity environments and AI development systems. The goal is not to bundle competing apps, clone their branded interfaces, or expose a thousand unrelated tabs. The goal is to retain the real editable meaning of work while a person moves smoothly among relevant capabilities.

PLATZ aims at the depth people associate with Unreal Engine, Unity, Blender, ZBrush, professional Adobe creation software, Clip Studio Paint, dedicated 2D game tools, Visual Studio-class development tools, and sophisticated AI research workbenches. These names describe categories of sophistication; they are not claims of partnerships, copied technology or immediate feature parity. PLATZ must build a distinct integrated experience in which an asset can be painted, modeled, shaded, animated, scripted, tested, played, published and revised without a maze of mandatory lossy exports and reimports.

One application presents six closely integrated responsibilities: **PLATZ Hub** for project discovery and launch; **PLATZ Studio** for adaptive creation, painting, modeling, programming and media work; **PLATZ Engine** for real GPU rendering, scenes and simulation; **PLATZ Runtime** for genuine play and standalone execution; **PLATZ Core** for source identities, revisions, permissions and recoverable data; and **PLATZ AI** for original specialist intelligence and authorized project-aware assistance. These are conceptual responsibilities, not a mandate to run them inside one process or to build separate end-user programs.

Its first reference development environment is a Windows desktop/workstation; future cross-platform authoring and exports should be architecturally considered and qualified individually rather than claimed automatically. Essential local authoring and playback should not require a forced external account, subscription or network connection. Network-dependent workflows must disclose their dependency and consent. The user's work remains theirs.

## 2. The defining advantage: live, editable, safe, understandable

**Live source unity.** A change to an editable 2D layer, pixel frame, procedural voxel object, 3D mesh, material, animation curve or gameplay rule should flow through a source-connected preview and the appropriate runtime representation without needless human export/reimport steps. Updates may be incremental or asynchronous; actual latency is measured, and the user sees when processing is pending. Derived GPU data must never become a hidden second source of truth.

**Real depth for non-coders.** A beginner can choose a task, recognize concepts such as World, Character, Item, Health, Dialogue, Camera and HUD, and make sophisticated interactive content without being forced to write syntax. Templates and guided workflows are accelerators, not ceilings. Advanced users can inspect properties precisely, edit code, debug logic, extend the system and customize the UI.

**One consistent project.** Changes across visual and textual tools honor stable object identity, dependency relationships, source lineage, undo/history, project recovery and explicit Play-state isolation. Team workflows and branches must not silently corrupt source. Game saves and editor saves are separate kinds of state.

**Safe project-aware intelligence.** PLATZ AI understands the authorized active work and can answer, plan, synthesize native editable assets, and stage many related changes. Actions are version-aware and limited to granted rights. The user can inspect a preview/diff, accept a complete candidate or selected safe parts, or discard it. Independent tests verify what can be tested; no AI may confer production approval upon itself.

**Infinite creative possibility is an aspiration, not infinite hardware.** PLATZ must resist unnecessary feature, detail or artistic limits. It must offer graceful quality tiers, meaningful error messages and efficient workload scheduling. It may not promise unlimited RAM, 16K rendering at every frame rate, automatic production of a complete commercial game or results better than every established product without evidence.

## 3. What success feels like to different creators

**Newcomer.** Open an offline Hub; find the right activity using plain language or search; create a local project; make a real change; press Play or preview; understand what happened; save, close and reopen without learning source-control internals. Related controls appear in context, while unused professional controls remain discoverable but unobtrusive.

**Game maker.** Create a world, sprites or models, modify assets, apply materials, animate characters, define gameplay rules, debug them, test controller and camera behavior, save game progress separately, and produce a qualified playable build. Advanced graphics and complex game systems remain accessible without forcing an external editor.

**Professional artist.** Use pressure-sensitive layered painting, precise color control, vector illustration, comics, complex mesh construction and sculpting, UV and retopology, surface painting, baking, shading, rigging, timeline, audio and VFX authoring. The application retains detailed native authoring data rather than treating flattened exports as the only permanent artifact.

**Software developer.** Use a serious IDE experience with project-aware navigation, typed editing, diagnostics, debugging, tests, profiling, version control and extensions. Implement behavior directly in code where advantageous while preserving the declared relationship to visual creation tools.

**AI creator/researcher.** Build, train, evaluate and run purpose-built, locally capable PLATZ specialists; manage data rights and verification; distinguish original from externally pretrained models; create editable assets and project-aware edits; coordinate multiple bounded workers when collaboration has measurable benefit.

**Teams and other creators.** Reuse, inspect, branch and share compatible content with rights and conflict handling; eventually use documents, data tools, animation/video/audio workspaces and other optional qualified domains. Shared UX concepts should remain recognizable even when a domain has its own specialized data representation.

## 4. What is deliberately not promised

PLATZ is not a merely decorative collection of screens; an Unreal-sized engine built overnight; a shell around proprietary competitor apps; a cloud-only assistant; a system that treats all content as interchangeable flat files; or an autonomous agent with unbounded account, spending and host privileges. The master does not require every product family to be release-ready at once. It does require honest current capability indicators and a credible long-term plan for each retained domain. Business model, marketplace revenue shares, royalty policies, fixed dates and mandatory external services are reserved owner decisions, not invented by an AI developer.

# PART II — THE COMPLETE CREATIVE EXPERIENCE

## 5. Hub, Studio, navigation and personal control

The Hub is the actual home for local projects, templates, installed capabilities, reusable resources, builds, recent activity and trusted help. Searching should retrieve objects, assets, commands, settings, docs and contextual tasks rather than requiring a user to know subsystem names. Projects show real paths/revisions and working launch methods. Unimplemented or incompatible features are clearly labeled, not made to look available through inactive decoration.

Studio provides appropriately contextual workspaces: scene/world, art, model, logic, animation, build/test, audio/video, code, data and any later qualified domain. A concise initial group such as **World, Art, Model, Logic, Animate and Build** is a useful design candidate, not an irreversible six-tab limitation. **Simple, Advanced and Developer** presentation modes share the *same* authoritative assets and project state. Creator-friendly keymap profiles are an appropriate capability, with names and exact bindings checked for license and usability issues.

PLATZ ultimately supports extensive end-user customization: colors, icons, fonts, density, contrast, menus, shortcuts, panels, docking, detached windows, multi-monitor positions, quick commands, macros and saved project/task layouts. Users should be able to visually author permitted UI layouts and extensions, optionally using code. Crucially, appearance customization cannot mask or spoof privileged approval, security, data deletion or Stop controls; safe default layouts and recovery remain accessible. Accessibility is a working behavior, not only a theme option: keyboard access, focus, screen-reader semantics, readable scaling, alternative cues, localization and right-to-left scripts require appropriate real testing.

PLATZ Engine must become a technically independent, source-connected game and simulation engine with its own strategic control over scene interpretation, rendering behavior, resource scheduling and runtime integration. Its editor and runtime must evolve **together from the first meaningful build**. A shell-only application is not the successful first engine slice: the first integration proof should demonstrate a real project object rendered by the chosen engine, selected and edited through Studio, interacted with by runtime, and saved/reopened correctly.

Rendering ambitions include pixel-accurate 2D, 2.5D, high-fidelity 3D, volumetric or hybrid content, sparse voxels, PBR materials, advanced direct/indirect illumination, ray and path tracing when qualified, reflections/refraction, shadows, subsurface/transparent effects, atmosphere/weather, realistic and stylized lighting, post-processing, GPU simulation, efficient dense geometry, streaming textures and terrain, and robust camera motion. Pixel/vector exactness must be protected from 3D tone-mapping and temporal filtering when these would corrupt intended colors or edges. Requested quality settings and actual activated settings must be clearly distinguished.

Simulation and gameplay ambitions include fixed/reproducible update behavior where needed, rigid/soft-body and continuous collision, 2D/3D movement, vehicles, destruction, cloth/hair/fluid effects, navigation/NPCs, inventories, crafting, quests, dialogue, RPG progression, real-time strategy and board/card rules, factories/ecosystems, physics-linked audio, haptics, audio mixing, multiplayer authority, headless servers and open-ended project-defined mechanics. Large scenes must maintain spatial precision, stable identities, efficient streaming and predictable error recovery.

Studio and Runtime consume compatible interpretations of the same saved source revision; runtime state is isolated from authoring state. A player checkpoint is not an editor revision. Play/Stop must not change permanent project data unless explicitly committed through an authorized, reversible action. Exports must declare qualified target environments, provenance, licenses, capabilities and exclusions; a standalone claim requires running a built artifact without developer-only dependencies.

## 7. 3D, worlds, characters, materials and procedural creation

A professional modeling and world-creation environment eventually supports parametric and polygon meshes, vertex/edge/face control, sculpting and multiresolution detail, nondestructive modifiers, UV unwrapping and packing, retopology, normal/AO/curvature baking, topology analysis, procedural geometry nodes, voxel sculpting and sparse storage, CAD-like precision or NURBS where appropriate, scan/photogrammetry workflows and loss-aware conversion among supported representations. Materials should permit node-based procedural authoring, direct mesh surface painting, layers and masks, texture sets, bake workflows, physically meaningful channels, custom shading where qualified, color-managed previews and performance diagnostics. A texture or material should be editable where it is genuinely created, not an unmodifiable screenshot of an advanced effect.

World authoring includes terrain, biomes, streaming/LOD, vast coordinate spaces, vegetation, clouds/weather, water, collision/navigation and optionally networked simulation. Users should be able to combine generated and manually authored elements without destroying overrides. Visual creation must progress beyond scattered spaghetti nodes. ## 10. PLATZ AI: original intelligence plus real creation tools

PLATZ AI must become an intelligent, locally capable colleague throughout the product, not merely an embedded generic chatbot. It should understand actual authorized objects, exact project revisions, relevant knowledge and user intent; explain, plan, code, troubleshoot, make edit proposals, synthesize native editable media or geometry, coordinate qualified specialists and verify results within explicit limits. Distinguish deterministic computation, retrieval, pretrained models, fine-tunes, distillation, and *models trained originally by PLATZ*; each must have truthful provenance and measured capability.

The long-term identity includes original small/specialized reasoning and decision models, verified file-first factual knowledge, reusable learned procedures, multimodal creation, a cooperating coordinator/critical reviewer/specialist team, project-scoped specialist creation, local model training and controlled improvement. Do not permanently make PLATZ a thin wrapper around third-party base models. Short-term external or open-weight local teachers may be selectively useful if legally compatible, clearly labeled and approved; from-scratch specialist research should begin when representative rights-cleared data and valid measurements make it practical. No arbitrary fixed model size or vendor is universally correct.

AI edits should use a versioned, machine-validated **Engine Command Registry** or equivalent authoritative operations rather than guessing internal files or directly overwriting opaque project storage. Each operation targets a stable identity and expected revision, obeys preconditions and recorded permissions, and produces a reviewable change. Long tasks may accumulate edits inside an isolated proposed revision; automated validation should check applicable schema/build, asset integrity, gameplay and visual results before user review. A safety-critical edit may need extra checks; an edit to a pure text note need not run a 3D headless playtest. An accepted edit is reversible and recorded with actual results. Stop/cancellation must prevent any subsequently unauthorized commit.

PLATZ AI must adapt workload scheduling to real GPU/RAM pressure. Interactive authoring takes priority where the user is working; asset generation and model training may pause, defer, reduce memory residency or run when idle with user permission. This is a managed policy, not a fixed 4-GB/10-GB/14-GB allocation that assumes every GPU and model behaves the same way. Claims of model quality require protected evaluations, negative tests, independent qualification and transparent limitations.

# PART III — SHARED PRODUCT TRUTHS AND SAFEGUARDS

## 12. Canonical editable project data and consistency

Every retained source element has a stable **ObjectIdentity** distinct from its display name and filesystem location. The authoritative **RevisionHead** identifies the accepted editable state; writes verify the expected revision to reject stale overwrites and race conditions. A typed, validated change (**TypedEdit** or equivalent) records target, preconditions, transaction scope, effects, provenance and safe reversal. Derived runtime/cache representations have explicit lineage, cache identity and rebuild paths; deleting a cache must not delete unique user work.

Editing is transactional across applicable source/metadata/blob stores; partial failures must not expose a falsely committed project. Recovery should preserve the last valid state and offer safe repair for corrupt settings or incompatible extensions. Undo/redo and branches work coherently across relevant tools, with visible consequences for shared assets and instances. Concurrent changes require conflict handling rather than last-writer-wins data loss. Save/Open must be validated against crash/restart/migration scenarios; alias names or relocated project files must not produce wrong-object edits.

Project objects do **not** all have to use the same physical representation: a mesh, vector document, video timeline, game-rule graph and spreadsheet can have optimal typed formats. Shared services provide consistent identity, references, access control, revisions and search. The engine can compile source hierarchies into GPU-friendly or cache-friendly runtime structures while leaving editable source intact. OpenUSD-like layer composition, MaterialX, glTF, content-addressed blobs and other interop standards are **candidates** evaluated per workflow, not prerequisites for adding every simple feature.

## 13. Separate authoring/runtime/AI states and safe automation

Three authorities must remain distinguishable: **editable authoring state**, **transient or checkpointed game/runtime state**, and **proposed AI staging state**. Gameplay cannot covertly mutate design-time assets. PLATZ AI cannot turn a proposal into an approved source revision by writing storage directly. Remote or plugin-generated data is untrusted until validated. Authoritative commits occur only through qualified host-controlled operations.

Permissions must be scoped to specific task, path/project, tool and duration. A **CapabilityGrant** represents rights actually enforced by the host; conversation text, web pages, plugins and models cannot mint stronger rights. A Stop operation revokes future authority, and commit paths must revalidate grants and source revisions at the point of durable write. Automated cancellation cannot promise to undo an already completed external action; that limitation must be disclosed.

Untrusted generated code, plugins or downloads require an appropriately isolated execution process with tested filesystem, network, CPU/memory and device permissions. A WebAssembly sandbox may be appropriate for selected components; it is not an automatic guarantee of safe native plugins or full host isolation. Security-critical approval, permission and cancellation controls may not be hidden, spoofed or disabled through user-authored themes or extensions. The application should preserve protected local data separation and refuse unauthorized model-training use.

## 14. Performance, fidelity and resource quality

Performance is measured as an end-to-end user experience: launch time, project loading, brush stroke response, selection/edit responsiveness, frame pacing, input latency, asset cooking, background work, save/recovery, runtime network responsiveness, audio dropouts, AI latency and resource usage. Frame rate is a function of device, quality settings, input scene and scale; no device-independent claim is meaningful. Publish p50/p95/p99 distributions where feasible, test representative heavy and light workloads and track regressions with baselines.

**Illustrative qualification profiles, not unconditional promises:** a low-resource profile might test pixel/2D and stylized 3D at 1080p on a 4-GB-class GPU; a midrange profile might test representative PBR scenes at 1440p on a 12-GB-class GPU; and a workstation profile might evaluate richer ray-traced content at 4K with appropriate reconstruction on a 16–24-GB-class GPU. A 60-FPS aspiration corresponds to a 16.67-ms frame budget, but scene, device, quality and method must be specified before it is treated as a release target. Treat 3-second startup, 2-second warm 1,000-asset project opening, 16-ms pen response, 8-ms selection, and 50-ms undo as **initial benchmark hypotheses to validate**, not invented passing results or permanent requirements on all systems.

The renderer, editor and PLATZ AI share resource limits. The product must prevent avoidable device-loss cascades and out-of-memory crashes through measured memory budgets, priority, graceful fallbacks, queuing/pausing and eviction strategies. Distinguish authored high-resolution data from currently resident or actually shaded pixels. A feature whose highest tier does not fit must degrade honestly rather than silently disabling correctness or losing editable assets.

## 15. Accessibility, interoperability, provenance and user sovereignty

Users should be able to work offline in essential supported domains and export compatible creations. Workspace layout, keyboard/screen-reader access, multiple monitors, DPI, display color management, localization, subtitles and controller remapping should be tested in supported configurations. Accessibility recommendations from WCAG2ICT are useful reference material; native software still needs practical testing.

Imported assets, generated content and exported builds retain appropriately inspectable license and creation metadata. C2PA/Content Credentials may be used when supported and relevant, but attaching a standard-specific manifest alone does not guarantee compliance with a storefront's current rules. Packaging must test the actual target platform, include needed resources, disclose missing features and preserve editable source. Online collaboration, markets and cloud acceleration must remain opt-in and respectful of user rights.

## 16. Safety boundaries that cannot be waived by a creator agent

Autonomous PLATZ development and PLATZ AI must never use the owner's personal accounts, payment methods, money, identity, credentials, subscriptions, private data or protected external accounts without appropriately specific authorization, and the standing project instruction disallows such use for autonomous experiments. No AI-registered external identity may be silently signed in on the owner's physical computer. Downloads and account creation, if separately approved, belong in isolated environments with honest anonymity and malware-risk limitations. Sensitive health, laboratory, real-person simulations and employer data demand distinct consent and qualification. Financial transactions, unauthorized private-data training and agent self-approval are out of scope for unreviewed autonomy.

# PART IV — ENGINEERING CHOICES THAT STAY SOUND

## 17. A real reference architecture, but not a permanent technology superstition

Before large production implementation, the developer selects a **coherent Reference Architecture Baseline** with a small number of authoritative Architecture Decision Records (ADRs). At minimum, decisions cover: (1) language/toolchain and UI framework, (2) rendering/control boundaries and target GPU APIs, (3) canonical project persistence and migration, (4) scene/asset/runtime projection, (5) visual logic, plugins and security isolation, and (6) AI models, tool registry and resource scheduling. Each ADR names the choice, alternatives, evidence, consequences, open risks and when it should be revisited. The chosen baseline remains stable across AI sessions until a justified migration is accepted.

**Design criteria:** real engine/editor/runtime sharing, source integrity, native interactive responsiveness, long-term graphics control, reasonable cross-platform path, modern accessible UI, security isolation, compatibility, licensing, tests, performance and future implementability. The developer should research only information likely to change the actual choice. Compare a small credible shortlist using official support data and representative working slices. Do not burn extensive AI usage comparing every language, re-litigating settled ADRs each session or pursuing a new release that has no relevant benefit.

**Candidate technology vocabulary, not mandates:** C++ or Rust for suitable native low-level components; .NET and other modern managed/native options where they win end-to-end; Vulkan, Metal and WebGPU through an appropriate abstraction; Qt, Slint or equivalent UI approaches if proven; SQLite and content-addressed asset stores; OpenUSD-like scene composition, MaterialX and OpenColorIO; appropriate 2D/3D physics; source-linked ECS or other efficient runtime projections; WASM/WASI for selected untrusted extensions; portable provenance schemes. These options may be rejected, combined or replaced with recorded evidence. No single option is blessed without a concrete project comparison.

A reference implementation is **binding to the active repository**, not binding to every future PLATZ release. Reverse expensive decisions through an ADR amendment, a compatibility plan, representative benchmarks and qualified independent review. Ordinary local design choices need not trigger bureaucracy.


### 17.1 Required latest-appropriate technology gate and primary engine ownership

Before the first consequential stack commitment, create an `ADR-000` decision gate that answers **what is the strongest modern engine-centered foundation for PLATZ**, considering the latest stable releases in the actual target environment. Compare a bounded shortlist including a first-class native C++/Rust engine path, a hybrid native-engine/managed-UI path, and an independently GPU-backed managed architecture if genuinely credible. Provide the current language/compiler/runtime versions, release/support status, rendering API and backend strategy, graphics resource ownership, capability to evolve toward real-time ray tracing and high-end GPU pipelines, scene/data independence, cross-platform implications, security, build/dependency cost and known risk.

**The available SDK list is inventory, not evidence of the best choice.** Do not automatically pick .NET 10, WPF, Qt, Vulkan, C++ or Rust because it is present, familiar or fastest. Specifically verify that newer stable versions exist; as of the edition date, .NET 11 is GA and is the first .NET version to evaluate if choosing .NET. An older major version may be considered for strong, reproducible compatibility reasons, but requires a documented exception and owner approval **before** becoming a greenfield baseline. Preview/nightly toolchains are not presumed better merely because they are newer than a stable release.

A managed or native interface framework **must not define the ceiling of the game renderer**. PLATZ controls the 3D pipeline architecture and source-to-GPU mapping. WPF or equivalent may be considered only as a shell *hosting a separately controlled modern GPU engine* if that interop is actually demonstrated and is competitive. WPF `Viewport3D`, `DrawingVisual`, CPU-side projected polygons, pseudo-depth sorting or a collection of 2D shapes are not accepted as the primary PLATZ 3D engine.

Selection evidence must include a concrete working native 3D render path for the top candidate, a quick high-information risk check of its UI/engine interop, and small quantitative resource/build observations. Do not over-research dozens of frameworks; when uncertainty remains, select a provisional architecture with an explicit validation gate, and implement no large dependent feature cluster until that gate passes.

### 17.2 A genuine permanent application, not a demo disguised as integration

The actual first usable PLATZ executable must present real Studio authoring tools backed by a canonical saved project; the same engine must project that scene into the actual renderer and Play mode. The first 3D project must support distinct editable objects, valid camera and world-space transforms, 3D depth and picking/selection, property editing and real scene persistence. A temporary cube, grid or shader test is permitted only as an internal verification fixture, **never as the delivered product or as evidence that PLATZ's intended professional functionality is complete**.

One long-lived verification project is required, but it is an **internal application test asset**, not an instruction to invent or polish an unrelated fictional game. Do not create a separate Signal Garden, museum, arena or other named product as a milestone. If an internal world has a name for clarity, that does not create a separate app, installer, roadmap or feature priority. The user must be able to open PLATZ and create an ordinary new project as well as open the internal verification world.

### 17.3 Decision record must be able to reject a convenient working choice

A successful `dotnet build` or attractive first-run screenshot proves buildability, **not architectural fitness**. `ADR-000` must explicitly distinguish (1) installed/available, (2) newest stable, (3) actually supported and compatible, (4) highest expected technical value and (5) independently demonstrated architecture risk. It must state conditions that would *reject* the chosen architecture. If a chosen path fails modern GPU ownership or source-connected 3D proof, pivot early while preserving source/assets and reusable infrastructure. Do not use sunk cost to justify expansion.

## 18. Independent proofs before expensive-to-reverse foundations

An initial real engine/editor/runtime source-connected slice is a first-class proof, not a prototype to discard. Before committing heavily to architecture, demonstrate the selected GPU renderer or equivalent verified fallback, actual project object identity, selection and inspector edit, Play/Stop or equivalent real runtime interaction, save/close/reopen, and a basic accessible layout. Show the code revision, build output, launch route, test transcript and resource observations. The foundational architecture is provisional until this proof and an independent challenge of the consequential choices.

Use risk-proportional comparison: if a choice is easily reversible and existing proof is sufficient, decide and implement. If it controls all future project files, isolates untrusted code or dictates rendering architecture, require stronger evidence. Do not halt all reversible engineering while waiting for an external reviewer. Do not allow either the author or the reviewer to claim a build was tested without executing it.

## 19. Data model, engine commands and failure-specific evidence

The repository must define enough concrete interfaces to prevent independently written subsystems from interpreting objects or revisions differently. A scene may have layered authored data and a compiled runtime projection, but the mapping from object identity to editor selection, GPU picking and runtime behavior must be testable. Material/geometry conversions must disclose when they cannot round-trip. Runtime objects never claim to own source-revision authority. Code and visual logic may share a typed intermediate representation or equivalent verified execution model; incompatible features must be identified rather than silently dropped.

AI commands and direct UI edits should meet the same validation and authorization rules. A typed change must reject stale revision, duplicate or invalid ID, failed preconditions, unauthorized path/network, and conflicting manual edit. A stopped task must not commit later merely because a subprocess completed. Run targeted adversarial tests around actual threat boundaries, not generic security slogans. Preserve last-good revisions under power-loss simulations and rollback tests. Document the accepted error and recovery behavior, not just the happy path.

## 20. Working performance targets and honest qualification

Adopt platform/workload-specific benchmark profiles and publish expected versus observed values. Examples may include 1080p/1440p/4K target classes, p50/p95 frame time, input-to-display latency, scene open duration, resident VRAM, shader build stalls and recoverability after GPU device loss. Numerical thresholds must be qualified on named hardware and approved by the owner/reviewer when they become release gates; they may evolve as measurements improve. Avoid falsely equating frame times in an empty scene with production-scale performance.

Export qualification begins with the actually built and tested target OS; Windows desktop is the initial user platform. Later Linux, macOS, browser, mobile, console and XR targets are separate verified targets, with platform-specific toolchains, rights and storefront requirements. Never claim a console exporter is ready without the relevant platform access and certification. Developer agents do not sign in to personal or store accounts to test shipping.

# PART V — DELIVERY THAT BUILDS MORE COMPLETE FEATURES

## 21. Release envelopes: decisive order without a brittle calendar

The complete catalog is the destination. The *active release envelope* is a limited set of user-visible outcomes and minimum reliability boundaries selected from actual dependencies and supported resources; it must be updated with approval as the application matures. This stops a developer from switching randomly between video editing, office documents and ray-traced worlds every session, while retaining all those long-term capability goals.

**Envelope A — Authentic foundation.** One real launchable PLATZ app with true GPU 3D, not a standalone demo or CPU-isometric mock; well-designed Hub/Studio essentials; actual engine view and editable scene; runtime interaction; canonical save/reopen and undo; first persistent validation world; build/test/launch paths; initial resource telemetry; foundations for controlled AI tools. Success is a working source-linked slice, not a shell screenshot.

**Envelope B — Create a complete playable experience.** Richer scene/asset authoring; reliable physics/input/camera; accessible no-code game logic and debugging; 2D/pixel/voxel/3D essentials and material controls; game save distinct from authoring save; functional audio/HUD; qualified standalone build; initial useful project-aware AI operations. The world becomes an expanding test and game experience.

**Envelope C — Professional creative depth and high-end rendering.** Deliberate improvements across modeling/sculpting, texture/material creation, 2D/illustration, rigs/animation, advanced lighting, streaming and procedural systems; refinements to no-code and code parity; performance, accessibility and robust export/migration. Do not add empty tabs for missing deep workflows.

**Envelope D — Universal creative breadth and advanced intelligence.** Advanced audio/video, productivity/data, collaboration, XR and future optional domains as justified; expanded original specialist model research and qualified multimodal creation; safe controlled self-improvement; broader packaging and ecosystems. Original PLATZ AI research should proceed in parallel with earlier envelopes where it does not compromise core app progress; it is not postponed until everything else is finished.

Envelopes are acceptance-oriented priority classes, **not fixed month counts**. Work may overlap where dependencies and qualified staffing permit. The actual developer must choose the most valuable *complete cluster* of capabilities in each session while keeping the active envelope and global priorities visible.

## 22. Whole-feature integration contract with realistic activation

Every feature has a **surface matrix**. A surface becomes mandatory when the feature genuinely affects it and its foundational service exists; absence of an unbuilt future subsystem does not force a fake integration. However, no feature may claim an already-supported product surface was updated if it was not. The matrix records `APPLICABLE/PASSED`, `APPLICABLE/FAILED`, `NOT YET AVAILABLE`, `NOT APPLICABLE WITH REASON`, and the exact test evidence. `NOT YET AVAILABLE` means feature scope is partial or that a future integration obligation is explicitly tracked—not silently accepted as complete if the user-facing promise depends on it.

- **1. Functional behavior:** **Always.** Actual working behavior with positive and negative cases
- **2. User interface / UX:** **Always for user-visible features.** Discoverable, visually coherent, error states and task flow
- **3. Canonical data / revisions:** **Always when data is authored.** Save, reload, stable IDs, undo/recovery
- **4. Engine and Runtime:** **Required whenever feature affects simulation, preview, rendering or play.** From the first real engine slice
- **5. No-code / code interface:** **Required when an existing supported logic/programming capability should expose this feature.** Future parity tracked where unavailable
- **6. PLATZ AI tools:** **Required when AI control is an advertised supported capability and an authorized API exists.** Otherwise future work is explicit
- **7. Search/help/configuration:** **Required when user needs to discover, configure or understand the feature.** Avoid doc bloat
- **8. Accessibility / localization:** **Required for user-visible controls.** Actual keyboard/focus/text semantics and relevant translations
- **9. Performance / resource use:** **Always proportional.** No obvious regressions; measure demanding paths that materially changed
- **10. Security / privacy / permissions:** **Always.** No unintended privilege, information flow or execution boundary changes
- **11. Automated & integration tests:** **Always.** Targeted tests; broader regression when interacting with shared services
- **12. Persistent validation world:** **When the capability can meaningfully be exercised there.** Otherwise use the proper test fixture

A feature may be delivered in an explicitly labeled **supported bounded scope**, not falsely advertised as professional parity. A user may have a useful working basic material editor before advanced ray-traced shader graph features exist. The completed basic scope must nevertheless have proper UI, persistence, correctness and tests, and the remaining advanced scope stays visible in the backlog. This distinction allows both rapid feature growth and dependable product quality.

## 23. Meaningful integrated development batches

Prefer cohesive groups whose shared infrastructure makes several user workflows more capable, rather than tiny cosmetic patches or unfinished parallel subsystems. A batch might improve project hierarchy, object picking, transforms, inspector editing and save/reopen together; another might deepen materials, lighting, selection/preview and GPU diagnostics; another might integrate visual rules, input, inventory, HUD and actual gameplay saving. These are **examples**, not commands to create prescribed games or file names.

A session is successful when there is verified improvement in the real application, honest evidence and a recoverable next step. A complex single infrastructure repair can be the right investment when it unlocks substantial later capability or prevents data loss. The developer may not endlessly declare those repairs complete without visible user benefit. Do not count source lines, empty folders, AI messages, invented benchmarks or unrun tests as features. Always update affected Studio/HUB navigation alongside new engine/workflow capabilities.

## 24. One enduring interactive validation world

PLATZ shall maintain **one primary living project** once the engine can open real projects. It is a genuine editable and playable scene/world where humans can move, click, inspect, trigger and test supported behaviors, while qualified AI agents can perform repeatable routes and read actual results. It grows cumulatively as rendering, materials, 2D, voxel, animation, physics, input, audio, HUD, gameplay, UI or AI services become available. It is not a separate test-game for each new milestone, nor a substitute for focused unit, crash, fuzz, resource, security or benchmark fixtures.

Every station has stable identity, setup/reset behavior, expected observable outcome, supported profiles, human instructions and automated test path if appropriate. Existing stations are rerun after affecting changes; failed stations remain visible. A project migration must preserve or explicitly adapt its old verification coverage. The same living world should increasingly demonstrate actual engine feature depth, useful art, coherent gameplay and correct project state—not just a wall of unrelated test buttons.

## 25. AI usage efficiency and loop interruption

Developer agents must spend scarce model context, research calls and tool invocations on actual decisions and working changes. At session start consult the small entrypoint, active ADRs, feature ledger, current tests and task-relevant master sections. Do not re-read all enormous documents, search the web for every known fact, re-benchmark settled architecture or repeat a full build when only targeted tests are needed. Fresh research is justified by material uncertainty, changing support/security facts, expensive-to-reverse decisions or a demonstrable blocker. A concise record of what was learned should prevent repeat research in later sessions.

After **two materially similar failed attempts**, or two iterations without a new diagnostic result, detect a likely loop. Stop repeating the identical approach. Preserve logs, isolate the smallest reproducer, test one different hypothesis, reduce scope or request independent technical review. Do not merely increase token usage or produce another overview. If an approach fails repeatedly, propose a bounded alternative, record decision evidence and continue with useful independent work where safe. The rule protects against both endless micro-edits and premature abandonment of difficult but valuable work.

## 26. Repository, developer memory, progress and owner launch

Maintain one canonical repository and a single known project root, using normal source/build/test/content conventions appropriate to the selected stack. Keep generated artifacts separate from authored files and never create rival application shells for convenience. At minimum provide a compact stable developer entry point and maintain **CURRENT_HANDOFF**, **OWNER_STATUS** and **DECISIONS_AND_FEATURE_LEDGER** (names may follow native repository conventions). Those records state source revision, current work, chosen architecture, verified build/launch route, tests, validation world, open defects, active permissions, current release envelope, accepted feature scopes and the next valuable complete cluster. Verify files and commits before trusting prose.

For each meaningful session provide an initial scope statement, a few concise progress updates at real milestones, and a final owner-facing report. Updates should report achieved work or an actual blocker, not empty narration. On any deliverable with a working application, provide exact executable/installer path or truly reachable URL, prerequisites, supported OS, build/commit, how the owner can run it, and the basic first task they can try. A container-only binary is not automatically accessible on the owner's Windows desktop. Do not invent downloads or working links. No asynchronous progress claim is permitted without an actual configured, authorized runner.

## 27. Independent qualification and honest acceptance

The developer writes and runs tests, freezes an inspectable code candidate and prepares evidence; a separate reviewer accepts consequential architecture, security, migrations, major render/gameplay behavior and releases when required. No author may self-promote its own candidate or rewrite the frozen approved baseline. Reviews should reproduce code behavior and negative cases rather than trust the author's prose. Acceptance means a defined scope passed on a specific build and profile; it is not a declaration that PLATZ has reached its complete vision.

The project remains accountable for both **scope breadth** and **finished quality**. Planned domains remain in the master; active release scopes remain realistic; each implemented slice is deeply integrated; and subsequent work expands the app rather than re-planning it.

# PART VII — ACCEPTANCE, INDEPENDENT EVIDENCE AND FAILURE TESTS

## 28. The master completion contract

A capability's ID, purpose and evidence claim are independent of the developer's chosen code layout. For each **active** implementation scope, the repository must state: included user behavior, known exclusions, platforms/hardware, actual relevant surfaces, expected positive/negative behavior, source/asset migration concerns, current tests, acceptance owner and measured status. An implementation can earn `VERIFIED` for a deliberately bounded scope while the broader professional ambition of that capability remains `BACKLOG`. It cannot earn full parity merely by having a button or an attractive demo.

The user-facing Hub and release notes should expose actual available features and meaningful limits. The feature register defines the complete destination, not a requirement to claim every item complete before the product becomes useful. No release is accepted solely because the feature count, line count, issue count or generated file count increased.

## 29. Seven universal end-to-end acceptance journeys

**J-01 — Real engine/editor/runtime project.** On the actual supported desktop build, launch PLATZ, create an ordinary new project (not only the internal validation world), render genuine depth-tested three-dimensional geometry using an independently controlled GPU engine and perspective camera, select a stable-ID object, edit a typed property, run and interact with it, stop and return without corrupting authoring, save/close/reopen and verify source identity and visual result. Record executed tests and an owner-usable launch route.

**J-02 — No-code playable experience.** A non-coder creates a World, Character, Item, Collision/Interaction and HUD using available domain tools, wires a meaningful event/rule, observes the actual runtime, debugs the logic, saves the game separately from project authoring and resumes. Explicitly distinguish the minimal available version from future advanced visual logic.

**J-03 — Complete creative asset round-trip.** Create or import an editable sprite, 3D object, voxel or layered art source; adjust its native authoring representation, material and transform; use it inside a genuine scene; save/reload source and undo; and produce a qualified output without undisclosed flattening. Test a broken input and a source-to-derived invalidation.

**J-04 — Professional UI and accessibility.** Discover a capability by search or context, open it with mouse and keyboard, edit a value, change theme/layout or monitor configuration, recover a damaged layout, and verify that protected approvals/Stop remain accessible. Include an actual screen-reader or assisted input test for qualified accessible releases.

**J-05 — Authorized PLATZ AI edit.** Ask about a selected object, inspect grounded project evidence, stage a typed and revision-bound change, run applicable validators, preview and approve or discard, then prove rollback. Repeat with a stale source revision, invalid command, unauthorized path and late cancellation; all must fail safely. Clearly identify model provenance.

**J-06 — The living validation world (internal PLATZ test asset, never a second product).** Open the same enduring project, navigate old and new stations by walking or clicking, run automated reproducible routes if available, verify station reset and preservation across application upgrades, then compare evidence and performance. Use separate fuzz, crash and security fixtures only where one world cannot supply safe proof.

**J-07 — Independent release and export.** A reviewer uses the declared source revision and build instructions to reproduce a build, starts the actual application, performs a representative user task, executes relevant tests and verifies the precise delivered export on the claimed target. A local developer-only artifact does not count as a freely installable public release.

## 30. Mandatory adversarial negative-test families

These are **behavior and failure criteria**, not an instruction to implement all test fixtures before the corresponding subsystem exists. Once an area is activated, the applicable counterexamples become part of its qualification; before then they remain visible pending obligations.

- **N-01 Identity collision — Trigger:** Two different objects share a visible name. **Expected safe result:** Edits/picking affect only the correct stable identity.
- **N-02 Stale revision — Trigger:** AI or concurrent editor commits against an old state. **Expected safe result:** Conflict rejected or explicitly merged; no lost newer work.
- **N-03 Partial save — Trigger:** Crash between large-asset write and revision-head commit. **Expected safe result:** Reopen last complete state or recover validated transaction.
- **N-04 Corrupt derived cache — Trigger:** Delete or corrupt compiled GPU/cache content. **Expected safe result:** Rebuild from canonical source without losing authored work.
- **N-05 Dependency invalidation — Trigger:** Modify one source used by multiple instances. **Expected safe result:** Correct dependents update; unrelated sources stay intact.
- **N-06 Undo through mixed tools — Trigger:** Paint, modify material, move object, then undo selectively. **Expected safe result:** Coherent revisions and predictable affected content.
- **N-07 Runtime authoring leak — Trigger:** Change game object during Play and press Stop. **Expected safe result:** Authoring unchanged unless explicit approved apply-back.
- **N-08 Gameplay checkpoint drift — Trigger:** Save player inventory and quit. **Expected safe result:** Resume correct state separate from editor source.
- **N-09 Conservation failure — Trigger:** Interrupt an inventory/currency transfer or crafting save. **Expected safe result:** No duplicate/missing counted resources beyond declared rules.
- **N-10 NaN/physics edge — Trigger:** Invalid transforms, extreme velocities, unusual geometry. **Expected safe result:** Controlled error/fallback; no silent corruption or infinite loop.
- **N-11 GPU device loss — Trigger:** Reset driver or exhaust GPU allocation in test harness. **Expected safe result:** Graceful recovery, accurate error and saved project integrity.
- **N-12 VRAM contention — Trigger:** Rendering + local inference + generative burst. **Expected safe result:** UI remains viable or discloses controlled pause/degrade; no data loss.
- **N-13 Shader compile failure — Trigger:** Invalid/custom shader and missing effect asset. **Expected safe result:** Safe fallback, useful diagnostics and retained source material.
- **N-14 Pixel exactness — Trigger:** Render indexed sprite through a mixed 3D/2D project. **Expected safe result:** Source pixels/colors preserved within declared exactness mode.
- **N-15 Audio overload — Trigger:** Heavy GPU shader compile while game audio runs. **Expected safe result:** Measured underruns and graceful policy, not hidden corruption.
- **N-16 Invalid visual logic — Trigger:** Unreachable states, missing target and cycle. **Expected safe result:** Human-readable diagnosis with source reference before/at runtime.
- **N-17 AI wrong-object proposal — Trigger:** Similar names, stale object IDs or unsupported operation. **Expected safe result:** No durable wrong-object edit.
- **N-18 AI Stop race — Trigger:** Async tool finishes after cancellation. **Expected safe result:** No late unauthorized durable commit.
- **N-19 AI poisoned retrieval — Trigger:** External content attempts tool/permission instruction. **Expected safe result:** Data treated as evidence only; no privilege escalation.
- **N-20 Filesystem escape — Trigger:** `..`, symlinks, junction/reparse and short aliases. **Expected safe result:** Resolved path stays within authorized scope.
- **N-21 Plugin escape — Trigger:** Untrusted plugin requests network/file/device outside grant. **Expected safe result:** Host rejects request; resource quotas enforced.
- **N-22 Sensitive cross-zone leak — Trigger:** Index/retrieve/serve or train on protected content. **Expected safe result:** No unauthorized disclosure or training inclusion.
- **N-23 Self-approval — Trigger:** Candidate model/agent attempts to promote itself. **Expected safe result:** Independent acceptance boundary holds.
- **N-24 Hidden Stop/approval — Trigger:** Custom UI theme/extension hides or imitates secure controls. **Expected safe result:** Trusted controls remain accessible and authentic.
- **N-25 AI batch rollback — Trigger:** Revert AI batch after unrelated manual changes. **Expected safe result:** Reversal is scoped and preserves independent later work.
- **N-26 Schema migration — Trigger:** Open newer or partly incompatible project. **Expected safe result:** No silent deletion; read-only/import or safe failure with diagnostics.
- **N-27 Export independence — Trigger:** Try standalone build on clean target. **Expected safe result:** Reports real prerequisites and fails honestly if unsupported.
- **N-28 Asset provenance — Trigger:** Generated/licensed media with missing rights. **Expected safe result:** Export warns/blocks according to declared rights policy.
- **N-29 UI accessibility — Trigger:** Keyboard-only, screen reader, display scaling. **Expected safe result:** Focus/labels/navigation work or limitation is disclosed as a blocker.
- **N-30 AI research loop — Trigger:** Two materially same failed attempts. **Expected safe result:** Strategy changes and preserves diagnostic evidence.

## 31. Progress and release evidence receipts

A meaningful completion receipt includes: source revision and reproducible build command; source files changed; current release envelope and activated capabilities; owner-observable workflows completed; applicable surface-matrix outcomes; target test commands and exact pass/fail/skip counts; existing validation-world stations and their results; relevant CPU/GPU/memory numbers; known defects, missing approvals and risk; security test evidence for changed rights; screenshots **only if captured from the actual running software**; and the exact supported launch/install path. The owner report must separate a working Windows installer, an executable in an AI cloud workspace, a source-only repository and a local development preview.

For consequential changes, independent acceptance attaches a different reviewer's name/identity, candidate hash and actual reproduced evidence. A failed independent gate returns to active repair; a developer cannot declare its own candidate promoted. The first owner-accepted master is frozen byte-for-byte, while later approved current editions remain versioned and traceable. No approval record should be fabricated.

## 32. Efficient reviewer and developer continuation

At session start read a small stable developer entrypoint, CURRENT_HANDOFF, OWNER_STATUS and DECISIONS_AND_FEATURE_LEDGER, then verify the actual repository state. Read only the task-related master sections unless major product direction is at issue; review the complete master when establishing the first architecture or making a cross-domain major change. Avoid reinterpreting a decision already settled by evidence. At session end finish the work safely, record exact tested behavior, check old relevant functionality, update the handoff and leave the next complete feature cluster. A developer is expected to make large useful progress when feasible, but not to skip essential correctness to inflate the feature count.

# PART VIII — GLOSSARY, SCOPE AND REFERENCE STANDARDS

## 33. Core glossary

**Authoring source:** Canonical editable data a user can reopen and meaningfully modify. **Derived asset:** Rebuildable optimized representation used for preview, rendering, execution or export. **ObjectIdentity:** Stable object reference independent of display name. **RevisionHead:** Exact authoritative source revision used for conflict detection. **TypedEdit:** Validated operation with target, preconditions and effects. **CapabilityGrant:** Host-enforced permission for a limited operation and scope. **Staging branch:** Proposed changes not yet accepted into permanent authoring state. **Runtime checkpoint:** Gameplay progress separate from the author's project revision. **Engine command registry:** Versioned authorized operations connecting UI, AI and Core rather than arbitrary file overwrites. **Living validation world:** One long-lived human/AI interactive integration project with stable test stations. **Release envelope:** The bounded set of genuine end-to-end outcomes pursued for a particular qualified build. **ADR:** A reasoned, reversible architecture decision recorded in the actual repository. **Verification:** Real tests tied to named source/build/device/workload. **Acceptance:** A separate qualified approval of relevant evidence. **Long-term capability:** Intended future functionality not represented as presently delivered.
