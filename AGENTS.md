# Developing PLATZ

1. Start with [START_HERE.md](START_HERE.md), [CURRENT_HANDOFF.md](CURRENT_HANDOFF.md), [OWNER_STATUS.md](OWNER_STATUS.md), and the [decisions and feature ledger](DECISIONS_AND_FEATURE_LEDGER.md). Check Git and the actual build before making claims.
2. The [PLATZ Master](docs/authority/PLATZ_MASTER_ENGINE_FIRST_V4.md) is the permanent product specification. The [developer directive](docs/authority/PLATZ_DEVELOPER_DIRECTIVE_ENGINE_FIRST_V4.md) and [Vulkan steering](docs/authority/PLATZ_VULKAN_FIRST_COMPLETE_STEERING_PROMPT.md) govern implementation. Read the affected Master sections, especially §§21–27 for delivery. Read the entire Master for a foundational or cross-domain correction, or when requested by the owner. The ADRs govern the existing implementation.
3. Follow one integrated workflow through discovery, Studio, Core, renderer and Play where applicable. Identify the affected Master IDs and surfaces in the ledger. Carry forward existing IDs, compatibility, accessibility and recovery checks. Track unavailable runtime, visual-code and AI integrations explicitly.
4. Use the one release executable under `out/Release` and the **Open validation workspace** command. This opens the same editable workspace under `.local/validation` across builds. Interactive authoring uses that workspace. Automated tests that mutate, inject failures or check restart use isolated copies of the tracked validation project, with focused technical fixtures where appropriate. Preserve tracked validation bytes unless the owner approves an evolution that retains the existing stations. Keep the owner's live Studio session intact. Schedule a single launch or restart to use the newly verified executable when possible.
5. For each delivered build, advance the CMake product version, rebuild the Release executable, and verify that the version in Windows properties and Studio matches. The project revision serves authoring and concurrency. Update the handoff with source commit, actual executable hash, supported hardware, tests, remaining defects and the next cohesive task.
6. Active approval gates include project-schema changes, changes to the tracked validation project, new dependencies, and an external asset store. Keep candidate results separate from independent acceptance, and protect reviewer-controlled evidence.
